### 二、第一阶段业务边界

#### 1. 一期必须完成的业务闭环
第一阶段目标是完成健身房运营最小闭环：

1. 后台可维护门店、教练、课程、卡项方案
2. 后台可维护会员档案
3. 后台可进行排课
4. 会员可在小程序预约课程并发起签到
5. 教练可在 App 中接收签到结果并完成私教课核销
6. 用户可购卡/购课，后台可查看订单
7. 后台可查看会员权益（卡、课包、剩余次数、有效期）
8. 后台具备基础经营统计能力
9. 小程序端与教练 App 具备一期页面骨架与核心流程演示能力


#### 2. 一期涉及的核心业务表
与一期业务直接对应的核心表如下：

- `fit_store`
- `fit_member`
- `fit_coach`
- `fit_course`
- `fit_course_schedule`
- `fit_course_reservation`
- `fit_checkin_record`
- `fit_card_plan`
- `fit_member_card`
- `fit_order`
- `fit_order_item`

#### 3. 一期暂缓实现的内容
以下能力建议暂不进入第一阶段开发主线：

- 多商户入驻界面
- 复杂营销中心
- 优惠券系统
- 会员标签精细化运营
- 教练绩效明细
- 商品库存管理
- 支付流水细分表
- 复杂审批工作流

这些内容在架构上可以预留，但一期界面和流程不强制上线。

### 三、一期角色设计与数据权限建议

#### 1. 角色划分
建议第一阶段后台管理端使用以下角色：

| 角色 | 说明 | 一期是否启用 | 数据范围 |
| --- | --- | --- | --- |
| `super_admin` | 平台超级管理员 | 是 | 全部数据 |
| `tenant_admin` | 商户管理员/总店管理员 | 是 | 当前租户全部门店 |
| `store_manager` | 门店店长 | 是 | 当前门店数据 |
| `front_desk` | 前台/会籍顾问 | 是 | 当前门店业务操作 |
| `coach_user` | 教练账号 | 是 | 本人课表、相关会员、预约与签到结果 |
| `finance_viewer` | 财务/运营查看 | 可选 | 当前租户订单与报表只读 |

#### 2. 一期权限边界建议

##### 2.1 `tenant_admin`
可访问：
- 工作台
- 门店管理
- 教练管理
- 会员管理
- 课程管理
- 卡项管理
- 订单中心
- 预约签到
- 基础报表
- 系统参数（部分）

##### 2.2 `store_manager`
可访问：
- 工作台
- 本门店教练管理
- 本门店会员管理
- 本门店课程与排课
- 本门店预约签到
- 本门店订单查询
- 本门店报表

##### 2.3 `front_desk`
可访问：
- 工作台（简版）
- 会员管理（新增/编辑/查询）
- 订单录入
- 办卡/续费/购课
- 预约查询
- 签到异常处理
- 会员权益查询


##### 2.4 `coach_user`
可访问：
- 教练 App 首页工作台
- 我的排课
- 待核销私教课
- 我的学员
- 学员签到确认与异常处理
- 本周课时与个人资料

#### 2.5 三端职责划分补充
- **PC 管理端**：供商户管理员、店长、前台、运营查看经营数据、配置门店、处理异常记录。
- **会员小程序**：供学员完成浏览、预约、购卡、签到、查看个人权益。
- **教练 App**：供教练移动查看排课、接收签到结果、完成私教课核销、查看学员信息。

#### 3. 数据权限实现建议

结合若依现有能力，一期建议采用：

- **租户级隔离**：通过 `tenant_id`
- **门店级隔离**：通过 `store_id`
- **员工角色控制**：通过 `sys_user + sys_role + sys_menu`
- **教练视角限制**：通过 `coach_id / user_id` 关联查询

一期建议先实现以下三档数据权限：

1. **全租户**：商户管理员
2. **当前门店**：店长、前台
3. **本人相关**：教练

### 四、管理端菜单设计原则

#### 1. 菜单设计原则
第一阶段后台菜单以“**业务闭环优先、结构清晰、便于生成代码**”为原则：

- 一级菜单数量控制在 6～9 个之间
- 复杂功能优先作为二级菜单，不做过深层级
- 主业务表尽量一张表对应一个主要管理页面
- 详情页、编辑页采用 **隐藏路由** 方式
- 菜单、路由、权限标识保持统一命名风格

#### 2. 若依路由风格建议
参考当前项目内置菜单风格，例如：

- `system/user/index`
- `system/role/index`
- `tool/gen/index`

一期健身房业务建议统一采用：

- **模块前缀**：`fitness`
- **页面组件路径**：`fitness/业务名/index`
- **详情组件路径**：`fitness/业务名/detail`
- **编辑组件路径**：`fitness/业务名/edit`
- **隐藏动态路由**：`业务名-detail/:id` 或 `业务名-edit/:id`

#### 3. 权限标识命名建议
统一使用：

- `fitness:store:list`
- `fitness:store:add`
- `fitness:store:edit`
- `fitness:store:remove`
- `fitness:member:list`
- `fitness:reservation:checkin`

即：

**`fitness:业务名:动作`**

#### 4. 包路径与业务模块建议
后端代码建议统一落到：

- **包名**：`org.dromara.fitness`
- **模块名**：`fitness`

如果使用代码生成器，后续配置建议统一为：

- `packageName = org.dromara.fitness`
- `moduleName = fitness`

### 五、第一阶段 UI 管理端菜单与路由方案

> 说明：本节按“**一级菜单 / 一级路径 / 二级菜单 / 二级路径 / 页面组件**”的方式明确落地。除 **首页** 外，其余一级菜单默认都只是菜单目录，不单独做页面。

#### 1. 一级菜单设计原则

- **首页**：是唯一一个“一级菜单本身就有页面”的菜单。
- **其它一级菜单**：都只做菜单目录，本身不做独立页面。
- **二级菜单**：才是实际打开页面的菜单项。
- **详情页、编辑页**：统一走隐藏路由，不出现在左侧菜单中。
- **模块统一前缀**：后台业务统一使用 `fitness` 前缀。

#### 2. 一级菜单清单

| 一级菜单 | 一级路径 | 是否有页面 | 组件 | 说明 |
| --- | --- | --- | --- | --- |
| 首页 | `/fitness-home` | 是 | `fitness/home/index` | 集成首页概览、经营看板、待办中心 |
| 门店管理 | `/fitness-store` | 否 | `Layout` | 仅作为门店相关菜单目录 |
| 人员管理 | `/fitness-staff` | 否 | `Layout` | 仅作为员工、教练、权限菜单目录 |
| 会员管理 | `/fitness-member` | 否 | `Layout` | 仅作为会员与权益菜单目录 |
| 课程中心 | `/fitness-course` | 否 | `Layout` | 仅作为课程、排课、预约、签到菜单目录 |
| 卡项中心 | `/fitness-card` | 否 | `Layout` | 仅作为卡项方案与持卡管理目录 |
| 订单中心 | `/fitness-order` | 否 | `Layout` | 仅作为订单相关菜单目录 |
| 报表中心 | `/fitness-report` | 否 | `Layout` | 仅作为经营报表菜单目录 |

### 六、页面职责拆解

> 说明：本节按 **第五章菜单顺序** 拆解页面职责，确保“菜单名称、完整访问路由、页面组件、页面职责”四项口径一致。

#### 1. 首页 `/fitness-home`
**页面组件**：`fitness/home/index`
**页面目标**：给商户管理员、店长、前台一个“今天要处理什么”的首页。

**对应数据库表分析**：
- **统计主表**：`fit_order`、`fit_member`、`fit_course_reservation`、`fit_checkin_record`
- **辅助维度表**：`fit_store`、`fit_course_schedule`、`fit_member_card`
- **分析说明**：本页不对应单一 CRUD 主表，而是按租户、门店、日期维度聚合经营指标、待办事项和到期提醒数据。

**建议展示模块**：
- 今日到店人数
- 今日新增会员
- 今日销售额
- 今日预约数
- 今日签到数
- 快捷操作入口（新增会员、快速开卡、快速排课、签到管理）
- 待处理事项（待签到课程、待支付订单、即将到期卡项）

**一期说明**：手工开发，不走生成器。

### 十二、结论
第一阶段业务设计建议围绕 **“主数据维护 → 交易生成 → 权益发放 → 会员小程序签到 → 教练 App 核销 → 基础报表”** 六步闭环推进。对于 UI 管理端，应优先把菜单、路由、页面职责、代码生成对象一次性统一下来；对于移动端，则应同步完成会员小程序和教练 App 的核心骨架，这样后续开发才能减少返工。

按本文档执行时，最推荐的起步顺序是：

1. **先建菜单与路由骨架**
2. **再生成主数据 CRUD**
3. **然后补订单、预约、持卡、签到、核销等核心业务逻辑**
4. **最后同步开发移动端小程序与教练 App 核心页面，完成签到-核销闭环联调**。
